# Architecture

The Stellar Contract Conformance framework is built on a layered architecture that clearly separates the rules of a standard from the mechanics of testing and the details of contract initialization. This separation ensures the core engine remains uncoupled from any specific standard (like SEP-41) and can support future profiles effortlessly.

## High-Level Flow

```text
SEP-41 Specification
        ↓
Conformance Profile
        ↓
Conformance Engine
        ↓
Setup / Fixture
        ↓
Soroban Test Environment
        ↓
Contract Under Test
        ↓
Behavior / State / Events
        ↓
Conformance Report
```

## Layer Responsibilities

### 1. Specification
The official definition of a standard (e.g., SEP-41 v0.5.2) maintained by the Stellar Development Foundation or community. This framework refers to the specification but does not define it.

### 2. Conformance Profile
A programmatic representation of a specific version of a specification. A profile defines the test cases, expected behaviors, required scenarios, and specific assertions that must be validated to claim conformance. It acts as the bridge between the human-readable standard and the test engine.

### 3. Conformance Engine
The reusable, core framework responsible for orchestrating tests. It does not know the details of SEP-41. Its responsibilities include:
- Managing the test lifecycle and context
- Executing scenarios and capturing panics/errors
- Applying assertions
- Collecting test results
- Generating the final report

### 4. Setup / Fixture
The abstraction layer responsible for initializing the contract under test. Since different contracts have different administrative and initialization interfaces, the conformance engine relies on an explicitly provided Setup/Fixture to prepare the environment (e.g., minting initial balances, setting administrators) before a test scenario executes. 

### 5. Contract Under Test
The compiled Soroban smart contract (WASM) being evaluated. It is treated as a black box that responds to specific profile-defined invocations.

### 6. Assertions (Behavior / State / Events)
The mechanisms used by the Conformance Profile to verify the Contract Under Test. They validate:
- **State transitions:** Inspecting storage or balance changes.
- **Events:** Ensuring required topics and data are emitted correctly.
- **Behavior:** Validating error paths, authorizations, and return values.

### 7. Conformance Report
The output generated by the Conformance Engine. It aggregates the results of all executed assertions into a structured format (both human-readable and machine-readable) for analysis.

## Extensibility
The architecture explicitly separates the Conformance Engine from the Conformance Profile. Future standards (e.g., SEP-50) can be supported by writing a new Conformance Profile and providing appropriate Setup Fixtures, without altering the underlying Conformance Engine. No external databases, RPC network interactions, or web applications are included in this architecture; all tests run deterministically within a local Soroban test environment.
